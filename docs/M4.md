# M4: pairing by QR code and the Apple Watch

M4 has two parts, and neither depends on the other. One sets the phone up from a scanned QR code; the other records on the Apple Watch. This page is the design note for both and the spike plan for the watch. Nothing here is built yet.

## Pairing by QR code

Today the phone is set up by typing the server URL and pasting an `ak_` key from the server's Keys page. With a QR code the Keys page shows the URL and a new key as one image, and the app's settings screen scans it.

**Status: waiting on a decision before any code.** The QR code carries a working key in plain view. Anyone who sees or photographs the screen while it is up can use that key until it is revoked. We have to decide whether that is acceptable, and with which limits (listed below).

### What changes in akou

The Keys page is part of akou's server-mode web page and already shows a new key once, in a dialog that removes it when it closes. The QR code would sit in that same dialog, so it lives exactly as long as the key's text does.

| File in akou | Change |
| --- | --- |
| [`src/ui/server-keys.ts`](https://github.com/GeiserX/akou/blob/main/src/ui/server-keys.ts) | A "Pair a phone" button that creates a `jobs` key named after the phone, then shows the QR code in the existing one-time dialog next to the key's text |
| a QR encoder | A small QR encoder for the browser page, either a dependency pinned to an exact version in `package.json`, or a vendored encoder under `src/ui/` with its license kept |
| [`tests/ui/server-page.test.ts`](https://github.com/GeiserX/akou/blob/main/tests/ui/server-page.test.ts) | The dialog shows the code for a new key and removes it when it closes |
| [`docs/ux/SERVER.md`](https://github.com/GeiserX/akou/blob/main/docs/ux/SERVER.md) | SV-U3 gains the QR code |
| [`docs/server.md`](https://github.com/GeiserX/akou/blob/main/docs/server.md) | How to pair a phone |

No route changes. The page creates the key with the existing `POST /v1/keys`, and the server stores nothing new.

### Payload (proposal)

One URL, so that the iPhone's own Camera app can open akou-companion directly and the in-app scanner reads the same text:

```text
akou-companion://pair?v=1&url=<server URL, percent-encoded>&key=<ak_ key>
```

- `v` is the payload version; the app refuses a version it does not know.
- `url` is the address the browser used to open the page (its origin), shown in an editable field before the code is drawn, because the address the browser uses may not be the one the phone reaches.
- `key` is a `jobs` key, never an `admin` key. The webhook secret is not in the code.
- The app applies the same `https`-or-private-address rule as typed settings, runs the server probe, and stores the key in the Keychain only once the probe passes.

### Limits to decide on

- Whether the QR code may carry a key at all, or should carry only the URL plus a short one-time code the phone exchanges for a key (a new akou route, more work, no key on screen).
- Whether a paired key should expire if the phone never uses it within some minutes.

### What changes in the app

A scanner on the settings screen (AVFoundation's metadata output for QR codes, with the camera usage string in `Info.plist`), and the `akou-companion` URL scheme in [`App/project.yml`](../App/project.yml) so the Camera app can hand the link over. Both fill the same two settings fields the user types into today.

## The Apple Watch recorder

The watch records the same Ogg Opus file the phone makes and sends it to the phone, which uploads it as a normal recording. The watch shows no live text and talks to no server ([DESIGN.md](DESIGN.md), M4).

### Spike plan

Each step ends with a result we can check; a step that fails stops the spike and is written up here.

1. **AkouOpus builds for watchOS.** [`Package.swift`](../Package.swift) already lists watchOS 11, but nothing has built it. Build AkouKit for the watchOS Simulator (`xcodebuild build -scheme AkouKit -destination 'generic/platform=watchOS Simulator'`) and prove that swift-opus 0.0.2 and the `COpusShim` target compile there. If swift-opus does not build for watchOS, the fallback is building libopus for watchOS ourselves, which is a bigger change to weigh before going on.
2. **A watchOS target that records to the same file.** Add a watch app target to the XcodeGen spec that records 16 kHz mono through `AVAudioEngine`, encodes with `OpusEncoder` and writes pages with `OggOpusWriter`, the same code the phone uses. It passes when the file made in the watchOS Simulator reads back through the same Ogg page checks as the phone's ([`OggTests`](../Tests/AkouKitTests/OggTests.swift)) and `ffprobe` reports Opus at 16 kHz mono.
3. **Hand the file to the phone.** The watch sends the finished file with WatchConnectivity's `transferFile`, with the recording's start time and length in the metadata. The phone receives it, moves it into its recordings folder and enqueues it in the upload queue (`UploadQueue`, from M1) as a normal recording, with the same idempotency key rule, so a repeated transfer uploads once.

### What needs a real Watch

The Simulator proves the build and the file format; these need a real Apple Watch paired with a real iPhone:

- The microphone path and the audio session on the watch (the Simulator's input is the Mac's microphone).
- Recording with the watch's screen off, and how long it can run before watchOS suspends the app.
- `transferFile` between two real devices: transfer time for a long recording, and a transfer that resumes after the phone was out of range.
- Battery drain per hour of recording.
